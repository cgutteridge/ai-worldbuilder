REFERENCE EVIDENCE TYPES
Updated: 17 Oct 2026

Types are stable classes of evidence question. Rules and queue language name
types; providers live in config/system-providers.json (nationwide+) and each
world's config/local-providers.json (below national), with the world catalogue
in that world's reference/SOURCES.txt. A provider may fill more than one type.

See GLOSSARY.md (Evidence / Provider / Streetlevel / Lidar / Aerial Review).

------------------------------------------------------------------------
THE FIVE TYPES
------------------------------------------------------------------------

vector_map
  Footprints, roads, landuse, OSM tags, plan geometry.
  Tendency: authoritative for plan; weak for materials and storeys.

poi_register
  Named entrances, protected trees, campus building ids, outline registers.
  Tendency: exact where/what-is-called; look still needed for appearance.

aerial
  Roof colour/form, ground surface, canopy cover, greeblie layout, rear wings.
  Tendency: strong for roofs and open ground; weak for wall detail and doors.
  (Tendency, not a hard rule — oblique or sharp streetlevel can beat a muddy aerial.)

streetlevel
  Storeys, walls, openings, doors, materials, street decor, entrance look.
  Tendency: strong for façades; weak for roof plan and back gardens.
  (Opposite of aerial in speech; not the ground layer of lawn/paving.)

lidar
  Absolute Y / massing. Products: DTM (bare earth), DSM (surface), diff = DSM−DTM.
  Tendency: heights only; never invent materials from it.
  Glue: scripts/lidar_provider.py (composite_world / tile_client). Catalogue rows
  that fill this type should set modules.world and modules.tiles (paths under the
  package, e.g. manage/… and get/…). Prefer type-facing class names LidarWorld /
  LidarTiles on those modules.

------------------------------------------------------------------------
PROVIDERS: SYSTEM VS LOCAL
------------------------------------------------------------------------

On add, ask **local vs system**. Rule of thumb: below national (UK / England)
→ local (world repo). Nationwide+ → system (this tool repo).

``config/system-providers.json`` holds system rows; the active world's
``config/local-providers.json`` holds local rows. Each provider has
``types: [...]``, licence (keep vs look-only), scope, and a cell checklist
``how`` when ``checklist`` is true.

Code lives under dual roots when a row sets ``package`` (e.g. ``providers/<id>``):

- system → ``ai-worldbuilder/providers/<id>/``
- world → ``<active-world>/providers/<id>/``

Resolve with ``cell_sources.provider_package_dir`` /
``script_env.resolve_provider_package``. Place URLs / ToS / fetch how:
active world ``reference/SOURCES.txt``.

Checklist / ``cell_sources.py --record`` keys are **provider ids**.
Alias: ``google`` → ``google-satellite``.

Adding a provider: skill ``add-data-source``. Scoring a candidate: ``evaluate-data-source``.

------------------------------------------------------------------------
CELL READINESS (intent)
------------------------------------------------------------------------

A cell is ready to build when every checklisted provider for that cell has been
tried once (HAVE or TRIED in the cell SOURCES guide) and none are STALE.
``cell_sources.source_status`` marks HAVE/TRIED evidence as STALE after
``STALE_DAYS`` (~6 months) from the newest manifest ``added`` date among hits,
or the last attempt ``date`` when there are no hits. ``--todo`` lists TODO and
STALE; ``--record`` allows a refresh without ``--retry-reason`` when the prior
attempt is stale. Still re-check earlier when evidence clearly disagrees with
the live world.

------------------------------------------------------------------------
AERIAL REVIEW
------------------------------------------------------------------------

Ring-ordered revisit of built cells against the best aerial evidence.
Progress lives in the cell registry (issues / layer flags), not a separate
AERIAL-REVIEW.txt file. Status conceptually: look → features → ground → trees → done.
Not a vendor name.
